## 1. 产品结论

Supplier 对标 1688 官方“分销 AI 工作台”、逸淘和爱用代发，提供一条完整的分销经营链路：

> **1688 货源 → 选品与利润判断 → 多店铺货 → 销售订单 → 1688 采购 → 物流发货 → 售后 → 经营分析**

产品不是独立的“AI 选品工具”，AI 应内嵌在选品、内容、定价、类目映射和风险检查中，减少操作步骤和错误，但不能成为基础铺货与履约的使用门槛。

### 必须追平

- 1688 采集、商品管理和多店铺货
- 标题、图片、价格、库存、上下架等批量经营能力
- 销售订单回流、1688 采购、物流同步和发货
- 售后、退款、采购与物流异常处理
- 多店铺经营和利润分析
- 服务市场订购、试用、续费、退款、到期、卸载及权益同步

### 必须更好

- **更简单**：新用户不依赖培训即可完成首次铺货，异常信息直接给出下一步动作
- **更安全**：所有自动化可暂停、可恢复、可审计；错单、漏单和重复副作用默认 fail-closed
- **更透明**：任务状态、失败原因、利润、套餐限制、AI 用量和附加费用清晰可见
- **目标更便宜**：在取证和单位经济验证后，让同等核心能力的公开到手价低于主流竞品；当前单平台核心版按不高于 199 元 / 年验证，同时通过轻基础设施、AI 配额和可选 BYOK 保持可持续毛利
- **更智能**：AI 给出可解释的利润、履约、退货和供应风险，而不是只生成文案

### 当前边界

- 首发只把 **抖店 + 1688** 做成真实、稳定、可售的闭环，再逐个平台扩张。
- 首发付款保持人工确认；未完成资金风控前不做免密自动支付。
- 响应式 Web 先验证产品价值；浏览器插件和独立移动端后置。
- 仅使用官方 OpenAPI，不使用账号 Cookie 或绕过平台规则的方案。
- 当前已创建的 Supabase 项目按 **staging / 内测环境**管理，不视为生产数据库；生产环境在 R3 独立核验或创建。
- 免密付款、全自动售后、AI 客服/视频、复杂团队权限、开放 API、私域社区、自有供应链、ERP/WMS 和自建 GPU 暂缓；只有 R5 的真实使用数据或明确 P0 客户需求才能恢复。

## 2. 推进原则

1. 真实闭环优先于平台数量，不能用“已接 OAuth”代表支持一个平台。
2. 对标基础经营能力优先于炫技功能，先解决铺货、订单、履约和售后。
3. 代码完成不等于产品完成；外部平台功能必须经过真实账号 E2E 才能标记完成。
4. 自动化必须可暂停、可恢复、可追踪，异常默认进入人工处置中心。
5. 核心业务服务只实现一套，各销售平台通过 adapter 复用。
6. 新平台按种子用户需求、市场价值和 OpenAPI 可用性逐个接入。
7. 套餐、限制、AI 次数和附加费用必须透明；低价不能依赖长期亏损补贴。
8. 生产安全优先于发布速度；[10-production-readiness.md](./10-production-readiness.md) 的 P0 未清零时不得宣称已可上线。

不使用完成百分比。“已有部分代码”写入交付物或证据列，但不能因此提升为“已完成”。只要仍缺少账号、资质、凭证或第三方环境，就使用“待外部条件”，不能提前使用“待真实验收”。

## 4. 当前实现基线

- 已有较完整的 AI 选品、评分、收藏对比、标题/详情生成、主图处理编排和智能定价基础。
- 抖店发布已具备类目、属性、资质、SKU、队列、幂等恢复、状态同步和库存联动的应用侧能力。
- 发布前预检已把权限、货源状态、利润试算凭证、目标店铺、标题、类目、属性、资质、SKU 和月度铺货额度收敛为一次只读检查；输入变化会使旧结果失效，正式提交仍重新执行权威校验。
- 订单同步、1688 采购、人工付款后的单包/多包物流回传、退款保护、异常核销和物流修复已有较强的安全基础。
- 经营看板已覆盖净 GMV、退款、采购净成本、预计毛利、热销和滞销。
- 目前只有抖店具备深度销售平台 adapter；淘宝、拼多多、快手、小红书和视频号尚未形成真实闭环。
- 自动免密支付、自动售后、统一异常中心、浏览器插件、独立移动端和服务市场商业生命周期尚未完成；批量经营工作台已进入“批量下架 + 批量改价”两个垂直切片，批量采集、标题/库存/SKU 编辑、上架、换源和清理仍未完成。
- 以上“已有”主要是应用侧和代码证据，不等于真实平台验收或生产可用。

### 必测异常目录

R1-05 至少覆盖：重复请求、平台超时且结果未知、迟到 worker、1688 取消/关闭、部分退款、物流消失、运单/承运商/商品映射变化、平台已成功但本地提交失败。

R2-03 的 P0 异常目录至少覆盖：发布驳回/死信、订单同步停滞、采购快照不一致、物流映射或回传失败、退款/售后待办、订购权益不一致。每种异常都必须显示业务对象、影响、原因、建议动作、重试/人工入口、责任记录和关闭证据。

## 6. 最合理的推进顺序

1. **现在推进 R0-03，并行推进 R0-04～R0-06**：先让免费内测环境可持续使用，同时准备账号、资质和测试权限。
2. **集中完成 R1**：先用真实抖店和 1688 小额订单证明从选品到履约、退款和异常恢复的闭环，期间不扩新平台。
3. **补齐 R2**：追平竞品日常经营底线，并把现有安全能力收敛成更容易理解的任务和异常体验。
4. **完成 R3**：订购权益、生产基础设施、定价和合规一起闭环，否则只是内部工具，不能售卖。
5. **执行 R4**：10–30 家种子商家分批内测，用真实数据修复 P0 问题，并将内测套餐校准成正式价格。
6. **进入 R5**：以“抖店 + 1688 单平台验证版”完成平台审核、生产订购验收和小流量灰度；此时不能宣称已追平竞品的多平台覆盖。
7. **R5 后按数据选择 R6 与 R7**：下一平台和高价值差异化能力可交替或有限并行，不必等全部平台完成才优化体验；但只有 R6 完成后才能宣称多平台基础能力追平。

## 7. 当前 Next 3

1. **R0-02 + R0-03，先形成可持续内测基线**：取得明确维护窗口后备份并预检 staging，一次应用第 34～37 个 migration、复核 37/37 与权限边界；随后轮换管理员 Key、重部署 Web/BFF，并用目标邮箱验收完整账号流。未执行这些动作前，当前结果仍只是代码与既有 staging 证据。
2. **R2-01 + R2-04，验证“更好用”**：服务端草稿、利润预检、冲突恢复、一次性用户绑定 OAuth 结果和自动化浏览器门禁已完成；应用 migration 后，让 5 名新用户独立完成“找货 → 利润/风险检查 → 修复阻断 → 授权 → 返回原商品发布”。
3. **R0-05 + R1，证明真实闭环**：准备抖店测试店、应用凭证与准确 scope、1688 买家授权、货源方案和小额测试预算，依次验收真实采集、发布、订单、采购、物流、退款与恢复。

不依赖外部账号的产品泳道按竞品差距推进：先做 R2-02 批量经营工作台，再做 R2-03 统一任务/异常中心；R2-05 售后工单与真实平台状态联动后收口。服务市场长交期事项继续按 R0-06 并行申请。

## 8. 后续跟踪规则

每次实现、联调或产品决策后，按以下顺序更新：

1. 在本文档更新对应工作包的状态、下一动作、阻塞、证据链接和日期。
2. 在 [09-main-flow.md](./09-main-flow.md) 追加代码、测试、真实 E2E 或部署证据；不在该文档改变产品优先级。
3. 若上线风险发生变化，同步更新 [10-production-readiness.md](./10-production-readiness.md) 的 P0 门禁和最近核验日期。
4. 只有范围、优先级、DoD、阶段顺序或状态发生变化时，才在下方变更记录追加一行。

状态变更约束：

- 外部平台能力：必须有真实账号、真实 API 和可追溯业务对象证据，才能从“待真实验收”改为“已完成”。
- 部署能力：必须有目标环境 URL、健康检查、日志或演练记录，不能只凭本地 Docker 通过。
- 商业能力：必须验证正常回调、重复回调、乱序回调、退款/到期和对账差异。
- 若证据过期或回归失败，状态必须回退，不允许保留绿色状态。
