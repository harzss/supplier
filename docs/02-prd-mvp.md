## 1. 版本定义

首发是 **抖店 + 1688 单销售平台验证版**，覆盖：

> 账号与授权 → 1688 找货 → 选品与利润预览 → 抖店铺货 → 销售订单回流 → 1688 采购 → 物流回传 → 售后/异常 → 经营复盘

该版本用于验证完整分销经营闭环和 1688 服务市场商业闭环，不代表已经追平竞品的多平台覆盖。淘宝、拼多多、快手、小红书和视频号必须在后续分别完成同一套真实 E2E，不能只展示入口或完成 OAuth。

## 2. 目标与非目标

### 2.1 产品目标

1. 新商家在一个工作台内完成从 1688 货源到抖店履约，不再拼接多个插件和表格。
2. 把错单、漏单、重复下单、重复发货、库存失真和售后断层变成可发现、可暂停、可恢复、可审计的状态。
3. 用 AI 降低选品、内容、类目和定价成本，但 AI 失败时不阻断基础经营链路。
4. 套餐、额度、AI 用量和附加费用透明，并在真实成本允许时提供可比口径下更低的价格。

### 2.2 首发非目标

- 不接入第二个销售平台。
- 不做免密自动付款；1688 付款保持人工确认。
- 不承诺全自动售后；高风险动作先进入人工工单。
- 不做完整 ERP、WMS、财务系统或供应链金融。
- 不做 Cookie 抓取或绕过平台规则的能力。
- 不做浏览器插件、独立移动端、AI 客服、视频生成和复杂团队权限。

## 3. 目标用户

### 3.1 主要用户

- 使用 1688 一件代发、在抖店试销的单人或小团队商家。
- 已经用采集/铺货工具，但被多插件、失败状态和售后切换困扰的商家。
- 对错单、漏单、库存和毛利敏感，但没有专职技术和运营系统的商家。

### 3.2 核心任务

> “我想快速判断一款 1688 商品是否值得卖，把它安全铺到抖店；出单后完成采购和发货，出问题时清楚知道发生了什么、下一步做什么。”

## 4. 核心用户旅程

```mermaid
flowchart LR
    A[注册并验证邮箱] --> B[绑定抖店与 1688]
    B --> C[搜索 1688 货源]
    C --> D[选品与利润/风险预览]
    D --> E[确认标题 图片 类目 SKU 价格]
    E --> F[发布到抖店]
    F --> G[订单回流]
    G --> H[创建 1688 采购单]
    H --> I[人工确认付款]
    I --> J[同步单包或多包物流]
    J --> K[回传抖店并跟踪售后]
    K --> L[利润与异常复盘]
```

任何一步失败都必须保留已确认输入和远端关联标识，允许用户安全重试或转人工处理，不能静默回退成空状态或重新产生不可逆副作用。

## 5. 产品原则

1. **真实状态优先**：页面显示的平台、订单和物流状态必须可追溯到最近一次同步时间。
2. **外部副作用幂等**：发布、采购、发货、退款/售后动作必须有稳定业务键和结果恢复路径。
3. **高风险动作 fail-closed**：商品、订单、地址、SKU、采购和包裹快照不一致时停止，不猜测、不跳过。
4. **人工付款**：首发不存储或执行免密支付凭证。
5. **AI 可降级**：AI 生成失败时允许使用人工内容继续；已计费阶段不能因重试重复收费。
6. **用户知道下一步**：每个阻断错误都显示影响对象、原因、建议动作、重试/人工入口和处理记录。
7. **只走官方 API**：所有平台交互遵守 OpenAPI、授权、配额、回调和数据使用要求。

## 7. 状态与自动化规则

- 商品、发布、订单、采购、物流、售后和权益均使用显式状态，不用空值推断成功。
- 状态只允许按定义迁移；远端旧响应不能把终态或新状态回退。
- worker 必须有持久所有权或租约；失去所有权后不再调用下一个外部接口或写入结果。
- 所有外部调用保存可公开的关联 ID、尝试次数和最近错误；日志不得保存 Token、Cookie、密钥、完整地址或原始手机号。
- 自动重试必须有上限、退避和死信；需要人工判断时停止重试并进入异常中心。
- 演示店、演示订单和 Mock 数据不能进入生产查询、额度、经营指标或真实 worker。

## 9. 首发 Definition of Done

只有以下条件全部满足，才能称为“抖店 + 1688 验证版可灰度”：

1. 真实 Supabase 账号完成注册、邮件确认、登录、刷新、退出、密码恢复和双租户隔离。
2. 真实 1688 授权完成搜索、详情、SKU/价格/库存、配额和曝光回传验收。
3. 真实抖店商品完成发布、审核状态同步、修改、上下架、库存变化和幂等恢复。
4. 真实销售订单完成订单回流、1688 创建采购、人工付款和单包物流回传。
5. 另一笔真实或平台认可的测试订单完成多包商品映射和抖店平台回读。
6. 重复请求、结果未知、取消/关闭、部分退款、物流消失/变化和迟到 worker 均完成演练，且无错采、漏单或重复外部副作用。
7. 100 SKU 批量任务具备预览、进度、逐项结果和幂等重试，成功率达到 95%；失败项可解释和恢复。
8. 服务市场订购、试用、续费、退款、到期、卸载、权益同步和对账的正常/重复/乱序/异常路径全部验收。
9. 10 家以上种子商家各完成至少 3 次真实闭环，全部 P0 缺陷关闭，并得到激活、履约、异常人工时、成本和付费意愿数据。
10. [生产准备度](./10-production-readiness.md) 的 P0 全部关闭，生产环境部署、备份、回滚、监控、告警和合规证据有效。

每项证据至少包含：环境、时间、租户/业务对象 ID、期望与实际结果、平台截图或回读、相关日志/审计 ID、发现问题及处理结论。不得在文档中记录密钥或完整个人信息。

## 10. 产品指标

### 激活

- 注册 → 完成账号绑定率
- 账号绑定 → 首次成功铺货率
- 注册 → 首次成功铺货的中位时间
- 首次铺货需要客服介入的比例

### 可靠性

- 发布、订单同步、采购和物流回传成功率
- 每 100 单的阻断异常数、重复副作用数和人工处理分钟数
- 恢复成功率、平均发现时间和平均解决时间

### 经营与商业

- 有完整成本依据的订单覆盖率
- 活跃商家 W1/W4 留存和持续铺货率
- 每商家的真实云、AI、客服和售后成本
- 试用 → 付费转化、退款率、贡献毛利和 NPS

目标值先由 3–5 家陪跑内测建立基线，再用于 10–30 家种子商家判断；未经数据验证，不沿用旧版 PRD 的“6 周、100 家、百万 SKU”等历史假设。

## 11. 后续版本

- R6：根据种子商家需求、市场价值和 OpenAPI 完整度选择下一销售平台，并重复本 PRD 的 OAuth、商品、库存、订单、履约和售后 DoD。
- R7：在真实数据上增加可解释供应风险、自动售后、替代货源、浏览器插件和移动关键待办。
- 每增加一个平台，必须新增对应的真实 E2E 证据和生产门禁，不能降低抖店首发的安全标准。
